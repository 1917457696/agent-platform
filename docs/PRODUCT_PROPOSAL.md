# AI 中医临床学习与实训平台产品方案

> 面向中医教育培训机构的产品提案。本文讨论未来正式产品，不把当前演示原型包装成已经上线的 SaaS。

## 一、业务背景

机构拥有老师、课程、医案、临床经验和训练营运营能力，但传统课程的价值主要停留在“老师讲过、学员看过”。学员是否真正理解、能否把知识迁移到病例、在哪一步出现错误，通常要依赖老师在社群或线下逐个判断。

机构希望逐步把传统中医培训升级为 AI 驱动的培训形式。真正要建设的不是一个通用聊天机器人，而是一套围绕课程学习和临床能力训练的数据化学习服务。

## 二、传统培训存在的问题

1. **学习结果不可见**：看完视频不等于掌握，机构很难知道学员在哪个知识点卡住。
2. **理论到临床有断层**：学员记住概念后，仍不知道面对医案先问什么、如何组织四诊信息、如何形成辨证依据。
3. **老师无法一对一覆盖**：老师的时间被重复答疑占用，真正需要经验判断的复杂问题反而得不到充分关注。
4. **病例训练难规模化**：高质量医案需要老师准备、扮演患者、点评和复盘，人数一多就难以持续。
5. **错误没有闭环**：学员的错题、遗漏问题和错误推理没有结构化沉淀，很难回到对应章节重新学习。
6. **课程内容缺少持续服务**：课程售卖通常是一次性内容交付，缺少学习陪伴、练习和复习机制。

## 三、为什么 AI 适合解决

- **检索与解释**：将老师课程、讲义和医案整理成可核对的知识库，回答回到指定课程体系。
- **对话式教学**：根据学员的问题、阶段和错误，换一种说法、追问或给出 Hint。
- **结构化模拟**：让 AI 扮演患者，按病例状态逐步透露信息，训练学员主动获取证据。
- **过程评价**：结合规则和模型解释，评价“问了什么、漏了什么、为什么重要”，不只给答案。
- **个性化推荐**：把错误关联回课程章节、病例和下一次训练。
- **教师协作**：AI 生成草稿，老师保留审核和教学决策权。

AI 不能替代中医教师、执业医师或机构的内容治理；高风险诊疗结论、处方和剂量必须保留人工审核。

## 四、目标用户

### 学员

目标是学懂知识、完成练习、训练临床思维，并知道下一步复习什么。关键任务包括课程问答、章节小测、医案训练、训练报告和个性化复习。

### 中医老师

目标是把个人经验和课程内容沉淀为可复用的教学资产，减少重复答疑，看到学员共性错误，并审核 AI 生成的反馈和题目。

### 培训机构

目标是把一次性课程升级为持续学习服务，提高课程完成和复购价值，形成可量化的学习数据，同时控制医疗安全、版权和内容风险。

## 五、产品定位

**AI 中医临床学习与实训平台**：以课程为入口，以 AI 导师为陪伴，以病例实训为能力验证，以教师审核和数据分析为质量保障。

它不是：

- 面向患者的自动诊断工具；
- 只把课程资料接入聊天框的 RAG Demo；
- 只会给标准答案的题库；
- 用一次模型评分代表学员临床能力的“智能测评”。

它要提供的是：

> 学 → 练 → 评 → 补 → 再练

## 六、核心学习闭环

```text
课程学习
  ↓
AI 课程导师：讲解、答疑、追问、举例
  ↓
章节练习：小测、错题、复习卡
  ↓
病例实训：模拟患者、主动问诊、自主辨证
  ↓
AI 临床教练：过程评价、遗漏解释、思维复盘
  ↓
薄弱项分析：四诊采集、病机分析、辨证依据、风险意识
  ↓
推荐课程 / 章节 / 病例
  ↓
再次训练
```

问诊 Agent 位于“病例实训”环节，是平台能力模块之一，而不是产品本体。

## 七、产品功能地图

### 学员端

- Learning Center：我的课程、学习进度、今日训练、推荐复习。
- 课程页：章节内容、课程资料、AI 课程导师、章节小测。
- 实训中心：推荐病例、训练目标、难度和预计时长。
- 病例训练：AI 患者、快捷追问、自由输入、初步判断提交。
- Training Report：问诊覆盖、遗漏解释、辨证依据、风险意识、下一步建议。
- 推荐学习：根据错误关联到课程章节、复习卡和下一份病例。

### 教师端

- 上传课程、字幕、PPT、PDF、讲义和老师医案。
- 管理知识单元、来源、版本和适用课程。
- 创建结构化病例、关键问题、教学目标和评分量表。
- 审核 AI 答案、题目、反馈草稿和高风险工单。
- 查看班级共性问题、章节薄弱点、错误分布和训练完成情况。
- 查看单个学员的能力画像和训练轨迹。

### 机构管理端

- 课程、老师、班级、训练营和权限管理。
- 模型、知识库、成本、调用量和安全事件监控。
- 内容版本、版权授权、审计记录和数据删除策略。
- 课程效果、学习完成、复购和教师工作量分析。

## 八、学员使用流程

1. 学员进入 Learning Center，看到正在学习的课程和推荐训练。
2. 选择《四诊合参与辨证论治》某一章节。
3. AI 课程导师根据课程资料讲解，允许学员追问、要求换一种解释或查看出处。
4. 完成章节小测，系统记录错题和不确定项。
5. 进入对应医案，AI 扮演患者，只按病例状态回答。
6. 学员主动问诊，补齐病程、寒热、汗出、痰、舌象、脉象等信息。
7. 学员提交辨证思路、依据和仍需排除的问题。
8. AI 临床教练生成过程反馈，解释遗漏项和错误推理。
9. 系统推荐回看章节和下一份训练，形成再学习。

## 九、老师使用流程

1. 上传或选择课程资料，确认老师、课程和章节归属。
2. 系统解析文档、字幕和问答，生成待审核知识单元。
3. 老师审核知识单元、来源、常见误区和禁答边界。
4. 老师创建病例，定义病情事实、关键问题、教学目标和风险点。
5. 系统根据学员训练生成反馈草稿和班级统计。
6. 老师审核高风险内容和重要反馈后发给学员。
7. 将高频错误、优秀回答和 Bad Case 反哺课程 FAQ、题库和评测集。

## 十、AI 技术架构

```text
课程资料 / 医案 / 题库
        ↓ 解析、切分、标注、版本管理
课程知识库 + 病例状态库 + 评测集
        ↓
API 网关 / 登录权限 / 会话隔离
        ↓
安全护栏 → 主控分流 → 课程导师 / 病例患者 / 临床教练 / 推荐服务
        ↓
混合检索、结构化规则、LLM 解释、教师审核
        ↓
学员端 / 教师端 / App API / 企微或小程序
        ↓
Trace、成本、Bad Case、学习数据和指标闭环
```

当前项目真实实现的是：React 单页前端、FastAPI API、LangGraph 主控与子图、RAG 检索、SSE 流式输出、会话级凭据隔离、本地 Trace 和结构化病例训练。正式产品还需要账号、数据库、内容管理、权限、异步任务和监控。

## 十一、知识库 / RAG 方案

### 内容分层

1. 课程原文：视频字幕、PPT、PDF、讲义。
2. 老师内容：医案、课堂问答、经验总结。
3. 教学标注：章节、知识点、难度、先修关系、适用人群。
4. 安全标注：教学解释、需要教师审核、禁止直接回答。

### 检索流程

```text
用户问题
 → 查询改写与术语归一化
 → 关键词 BM25 + 向量检索
 → RRF 融合与来源过滤
 → 课程 / 老师 / 章节权限过滤
 → 生成带出处回答
```

当前默认使用项目整理的 `data/tcm_demo.md` 和本地 BM25；配置 Embedding Key 且存在索引时，才启用向量 + BM25 混合检索。正式产品需要课程级知识空间、文档版本、权限过滤和教师审核。

## 十二、病例训练方案

病例必须是结构化对象，而不是只给模型一段自由文本：

- 病例背景和时间线；
- 可被追问的字段；
- 每个字段对应的回答范围；
- 关键问题和教学目标；
- 风险信号；
- 允许提示和禁止提前泄露的信息；
- 评分维度和教师量表。

当前 Demo 已实现胸痛、咳嗽、发热三个合成病例，AI 患者按关键词命中字段回答。正式产品要由中医教师创建和审核病例，并将病例事实、对话记录和训练报告迁移到服务端。

## 十三、AI 评价方案

建议采用 Rule + LLM + Human Review 三层：

1. **规则层**：关键问题覆盖、危险信号、是否提交判断、是否越界请求。
2. **模型层**：提问顺序、表达质量、辨证依据是否连贯、反馈自然语言解释。
3. **教师层**：重要训练结果、高风险内容、争议样本和评分量表校准。

评价输出不只写“正确/错误”，而应包含：

- 已获取的关键证据；
- 遗漏的信息；
- 为什么遗漏重要；
- 推理在哪一步跳跃；
- 下一次可以尝试的提问；
- 对应课程和复习建议。

## 十四、学员能力画像

长期记录后可形成多维画像：

- 四诊信息采集能力；
- 重点信息识别能力；
- 病机分析能力；
- 辨证依据完整度；
- 方剂知识理解；
- 风险意识和边界意识；
- 病例完成率、复习率和重复错误。

能力画像必须基于多次训练和教师校准，不能用一次模型评分宣称临床能力。

## 十五、数据闭环

```text
课程内容 → 学习行为 → 练习过程 → 评价结果 → 薄弱项
    ↑                                      ↓
课程更新 ← 教师审核 ← Bad Case ← 推荐训练 ← 学员复习
```

优先采集：问题类型、命中章节、来源点击、错题、训练覆盖、报告查看、教师采纳和转人工。涉及个人数据时必须最小化采集、脱敏、授权、审计和可删除。

## 十六、MVP

首期只做一个课程主题：

> 《四诊合参与辨证论治》 → AI 课程助教 → 章节小测 → 外感咳嗽医案 → 训练反馈 → 推荐回看章节

MVP 范围：

- 一套经过审核的课程资料；
- 课程问答与来源引用；
- 一组章节练习；
- 一套结构化医案；
- 学员提交辨证思路；
- 规则化训练报告；
- 教师审核占位和人工转接。

MVP 不做：

- 全量课程接入；
- 自动诊断、处方和剂量；
- 一开始重构完整 App；
- 复杂社交和直播功能；
- 没有真实数据支撑的学习效果承诺。

## 十七、第二阶段产品规划

- 课程上传、解析、知识单元审核；
- 老师创建病例和评分量表；
- 学员长期训练记录与能力画像；
- 教师端班级统计和 Bad Case 管理；
- 企微、小程序和 App API 接入；
- 评测集、灰度、模型成本和质量监控。

## 十八、长期产品规划

- 每位名师拥有自己的 AI 课程导师和知识空间；
- 按课程、班级、训练营提供多租户 SaaS；
- 课程内容、病例和学习数据形成机构资产；
- 教师、AI 和班主任协作的学习服务；
- 在合规边界内建立可解释的临床学习能力模型。

## 十九、商业价值

### 对学员

从一次性观看课程，升级为持续陪学、练习和复习服务；提高学习可见性和课程完成价值。

### 对老师

减少重复答疑，把精力放在高价值教学和审核上；让老师经验沉淀为可复用资产。

### 对机构

增强课程差异化、训练营服务能力和复购价值；建立课程质量和学习效果的可量化数据基础。

## 二十、当前技术限制

- 当前没有真实课程视频、老师原始资料和正式版权授权。
- 当前没有真实学员历史训练数据，能力画像只能做产品设计，不能声称已实现。
- 当前没有生产级账号、PostgreSQL 会话库、教师端和多租户权限。
- 当前知识库默认是本地 BM25；向量索引需要 Embedding Key 和显式构建。
- 当前病例和评分是前端确定性 Demo，不代表临床能力评估。
- 当前 SSE 是回答分片展示，不是模型供应商原生 token 流。
- 当前 Trace 默认本地记录，生产环境需要 Langfuse/LangSmith、日志、成本和告警治理。

## 二十一、三种状态标记

### 已实现

React 单页工作台、课程产品化说明区、问答 Agent、RAG/BM25、可选混合检索、SSE、对话记录、sessionStorage 凭据隔离、急症护栏、结构化病例训练、规则报告、Trace、响应式布局。

### Demo 可实现

固定课程资料的章节问答、固定知识点小测、教师审核占位、单次训练后的推荐章节、模拟学习画像、三到五个课程场景演示。

### 产品方案

课程上传解析、真实老师知识空间、长期能力画像、多租户账号、教师端、App 正式接入、版权治理、生产监控和规模化训练营运营。
